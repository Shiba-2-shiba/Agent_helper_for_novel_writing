# 日本語20万字小説に対応するリファクタリング設計書

作成日: 2026-10-23  
対象: Shiba-2-shiba/Agent_helper_for_novel_writing  
確認した基準コミット: `b8ea6f2a2e09dcbc51353953738e72e9305410fe`  
状態: ユーザー承認に基づき実装済み。検証結果は `../../validation/2026-10-23-novel-200k.md` を参照。既存の実作品の移行は未実施。

## 1. 目的と到達点

Codexなどの外部エージェントが、過去の展開・人物の知識・未回収の伏線を参照しながら、日本語20万字の小説をシーン単位で執筆・改稿・再開できるようにする。単に文字数の選択肢を増やすのではなく、作品が長くなっても「何を検査・承認したか」「どの情報が現在も有効か」「その時点で誰が何を知っているか」を混同しない土台を整える。

今回の実装完了は、20万字相当のデータで決定的テストが通り、実際のエージェント評価を実施できる状態を指す。文学的な完成度や、LLMによる20万字完走を自動テストだけで保証したとは扱わない。

### 維持するもの

- 本文の正本は既存のシーン `txt`。章メモ `body.md`、設定・アウトラインのMarkdownは編集可能なまま残す。
- 通常運用は `runtime-first`。全文を毎回プロンプトへ渡さない。
- 外部エージェントが読解・執筆・要約する。実行系にLLM API、ベクトルDB、外部検索サービスを追加しない。
- Python標準ライブラリを実行時の基本とし、テストにはpytestを使用する。READMEに記載されたPython 3.8以上の契約を、既存評価スクリプトを含むテストで確認する。
- 3万・5万・10万字、旧アウトライン名、旧シーン名をアダプターで維持する。無関係な全面書き換えはしない。

### 今回行わないもの

自動的な意味理解・矛盾判定の保証、クラウドLLMの組み込み、GUI、作品本文の自動改変、全作品の無断移行、任意の時間軸を自動推論する機能、20万字超の一般化、全モジュールの再設計。

### アプローチ比較

1. **採用: 既存runtimeの段階的強化。** txt/MarkdownとCLIを維持し、再現済み不具合、20万字設定、任意導入の記憶を順に加える。旧作品を保持しながら各段階で検証できる。
2. **不採用: 全面再設計・DB中心への移行。** 一貫性を作り直せる反面、既存資産の移行と回帰範囲が大きく、今回の目的には過剰。
3. **不採用: 目標文字数だけ倍増。** 最小変更だが、承認・状態・記憶・文脈量の問題が残る。

## 2. 現状と優先順位

確認対象では、目標値が3万・5万・10万字に限定され、初期化する章が5章固定。`prompt_utils.py` は1,136行で、目標値・パス・runtime選択・状態更新などを兼務している。

既存の長編補助は出発点として有効だが、`scene_summaries.jsonl` の要約は本文先頭140字の抜粋であり、出来事や伏線を理解した要約ではない。人物・スレッドの欄は空のまま生成される。また、関連シーンには未来シーンが混ざり得て、生成された `related_context_pack.md` は現行 `build_draft_prompt.py` の本文に組み込まれていない。

先に修正する4つの不変条件:

1. **検査と承認の結合**: 検査した本文と、承認する本文のシーンID・パス・ハッシュを一致させる。承認前に本文が変わった場合も止める。
2. **対象runtimeの厳密性**: 指定シーンのruntimeがなければ、別シーンの最新runtimeへ黙って切り替えない。
3. **状態の一貫性**: 依存欠落による `fail` がScene Ledgerでは `completed` になる等の食い違いをなくす。ファイル数を検査完了数と呼ばない。
4. **生成物の鮮度**: アウトラインだけでなく、実際に読んだ設定・本文・記憶・選択対象一覧への依存を追跡する。同じディレクトリにある別生成物が台帳の同じIDを上書きしない。

既存検証の基準は87テスト成功、ルールベースの最低回帰9件・境界回帰22件成功。これは既存スクリプトの基準であり、実際のCodex等の挙動を測った結果ではない。

## 3. 正本と派生物の境界

| 領域 | 正本 | 再生成・更新方針 |
|---|---|---|
| 本文 | シーン `txt` | 移行・healthでは変更しない |
| 設定と計画 | `01`〜`05`のMarkdown、プロジェクトのstate YAMLの設定部 | 編集可能。移行は対象フィールドのみ変更し、原本をバックアップ |
| 機械検査 | シーン別 `check_report.json` | 本文ハッシュと検査条件に拘束された結果 |
| 本文承認 | `runtime/approval_ledger.json` | 明示的な承認・取消だけで変更。本文変更で失効 |
| 意味的な物語記憶 | `story_memory/accepted.json` | 外部エージェントの提案を検証し、明示的に採用した記録。自動再生成・上書きしない |
| 作業状態 | 本文・検査・承認から導出する状態 | `story_state.json`、YAML進捗、Scene Ledgerのstatusへ同じ規則で投影 |
| runtime・抜粋・検索索引 | 正本からの派生物 | ハッシュと依存一覧で鮮度を判断。安全に再生成可能 |

`story_state.json` を意味的な事実と機械的進捗の両方の正本にしない。既存の `characters` / `threads` 等に手入力内容がある場合は削除せず、移行候補として報告し、勝手に新記憶へ採用しない。

## 4. 信頼できる検査・承認・状態

### 4.1 検査レポート v2

従来のレポート項目を残し、`version=2`、`scene_id`、`source_path`（project相対パス）、`source_hash`、`check_inputs`、`check_inputs_digest`、`scope`（`scene` / `standalone`）を追加する。`target_file` は互換読取用に維持する。ハッシュ規約は既存互換の `sha256-utf8-text-v1`、改行正規化を含むUTF-8読取結果に対するSHA-256と明記する。

承認では、現在の本文・対象ID・正規化パス・検査条件がレポートと一致することを要求する。`fail` は拒否、`warning` は既存の `--allow-warnings` が必要。本文や条件を変更した場合は再検査を要求する。古いハッシュなしレポートは表示可能だが、新たな承認には再検査が必要。

新しい承認レコードにも `scene_id`, `source_path`, `source_hash`, `check_inputs_digest` と検査入力のsnapshotを保存する。共有の承認検証関数をstatus・health・exportで使用し、古いruntimeを読み直すだけでなく正本から現在の有効な検査条件projectionを再計算する。承認後にLength Band・文体条件・必要依存が変われば、本文が不変でも承認はstaleとなり、再検査・再承認までexportしない。

既に記録された旧承認は本文ハッシュの一致を確認して維持する。ただし「旧形式の承認」と表示し、検査をさかのぼって保証したことにはしない。

### 4.2 runtime選択

新規生成時は `runtime_manifest.json` にversion、scene_id、mode、入力ダイジェスト、生成物一覧を記録する。`--runtime_dir` による明示指定でもID・modeを検証する。

- シーン指定あり: そのシーンのディレクトリを優先し、旧flat runtimeは埋め込まれたIDが一致した場合だけ使用する。別ID・不明IDへはフォールバックしない。
- シーン指定なしのprompt: 最新indexのIDとmanifestを照合して使用する。新たに `--scene` を追加し、通常手順では明示指定を推奨する。
- シーンファイルをcheckするときruntimeが未生成: アウトラインがあれば、そのシーンのprepareを行ってから検査する。生成不能なら理由とprepareコマンドを返す。
- `scene.txt` 等のID不明ファイルの従来の単独検査は維持する。ただし `scope=standalone` とし、本文承認・シーン完了・物語記憶更新には使用しない。別シーンのlatestを利用せず、明示の設定か旧flatの文体設定だけを使う。
- 同一シーンIDの本文が複数パスにある場合は曖昧として停止し、どちらかを勝手に選ばない。

### 4.3 状態の意味

互換性のためScene Ledgerの `completed` は「現在の本文で機械検査がpass」を意味し、編集者の承認や小説の完成と同一視しない。

| 条件 | 執筆状態 | 承認状態 |
|---|---|---|
| 本文なし | planned | none |
| 本文あり、検査なし・古い検査 | drafted | none / stale |
| 現行検査fail | needs_repair | none / stale |
| 現行検査warning | drafted | 明示承認があればapproved |
| 現行検査pass | completed | 明示承認があればapproved |

`written_scene_count`、`checked_scene_count`、`completed_scene_count`、`approved_scene_count` を分離する。`last_completed_scene` は有効なpassの最大シーン順とし、fail時に対象へ進めない。既存の名前が不正確な `count_completed_scene_files()` は互換APIとして残して非推奨化し、新しい進捗の集計には使用しない。

## 5. 原子的保存と依存追跡

### 保存

JSON書込みは同一ディレクトリの一時ファイルへ保存し、flush・fsync後に `os.replace`。欠損時の初期値と、存在するが壊れているファイルを区別する。壊れた承認・記憶・台帳を空のデータで上書きしない。CLIにはファイル名と復旧方法を出す。

意味記憶・移行・承認台帳のapprove/revoke/refresh・共有状態投影など、すべてのread-modify-writeはproject単位の排他的ロックを使う。記憶には期待リビジョン、移行には期待ハッシュも併用し、二重実行で更新を失わない。公開操作が一度だけロックを取得し、内部のlocked helperは入れ子取得しない。残ったロックは理由を表示して停止し、自動削除しない。複数ファイル更新を単一の原子的操作とは称さず、ジャーナル・バックアップ・再実行可能な投影で復旧する。

### 依存

生成物IDは `artifact:<project相対POSIXパス>` とし、typeは別フィールドに持つ。同じIDの異なるパス登録を拒否する。

依存には、ファイル内容、任意ファイルの存在・欠損、シーン候補一覧のmembership、実際に使用した設定projection、必要な生成物のダイジェストを含める。選択候補の追加・削除でも検索結果が変わるため、選ばれた3件だけを追跡してはならない。

state YAMLの `active_work` や進捗を更新しただけで自分の検査結果が古くなる循環を避け、検査は文字数帯・文体・依存契約など使用した設定だけを追跡する。runtimeの再開情報が進捗を読む場合は、その進捗projectionも追跡する。初回は正しさを優先して全候補のハッシュを確認し、部分再生成・永続キャッシュの高度化は測定後の別改善とする。

healthは確認時に鮮度を再計算する。新形式のstale runtimeから通常のdraft/expandを生成することは拒否する。旧形式の不十分な依存台帳は未検証として警告し再生成へ案内し、最新の証拠へ勝手に昇格しない。

## 6. 20万字プロファイルと章構成

目標値の唯一の定義を `novel_agent/length_profiles.py` に置く。

| total | profile | planning_gate_min_chars |
|---:|---|---:|
| 30000 | novel_30k | 24000 |
| 50000 | novel_50k | 40000 |
| 100000 | novel_100k | 80000 |
| 200000 | novel_200k | 160000 |

計画ゲートは今回、従来の「計画したシーンの最小字数合計が目標の80%以上」を維持する。新たな粗密可変ゲートや章ごとの逐次ゲートは導入しない。20万字なら最低16万字相当の計画が必要であり、100シーン×standard最小1,600字が一つの例になる。100シーンや20章を作品の強制構造にはしない。

1シーンの帯は既存のbridge 1200/1500/1800、standard 1600/2000/2400、anchor 2200/2700/3200、climax 2600/3200/3800を維持する。全体文字数に比例して1シーンを引き延ばさない。

`init_project.py --chapter-count N` を追加する。省略時は全プロファイルで旧5章を維持し、20万字の実用例では `--chapter-count 20` を示す。指定時は1以上の任意章数を生成し、`chapter_1`〜`chapter_N` と空のChapter Cardを対応させる。旧ディレクトリ名は移動・改名しない。章番号は10以上でも数値順とする。部はアウトラインの任意 `part_id` メタデータで章に関連付け、本文パスに部階層を強制しない。

## 7. 10万字から20万字への安全な移行

新しい目標変更はdry-runで差分と影響を確認してからapplyする。

1. 明示目標200000を受け取り、canonical total/profile、planning target/gateを一緒に更新する。
2. 旧既定値の `planning_gate_min_chars=80000`、`planning_target_total_chars=100000`、旧 `total_chars` があれば残存overrideとして検出する。目標変更時に既定値由来のものは160000/200000へ揃える。
3. 独自のゲート値は黙って維持・上書きしない。dry-runをconflictにして、`--gate-policy profile`（16万へ変更）または `--gate-policy preserve`（値を保持しcustomと記録）を選ばせる。新規作成の既定はprofile。
4. 目標値を変えると、従来の `planning_gate_status=ready` は `blocked` に戻す。現在のアウトライン合計と不足分を出し、20万字の計画承認を継承しない。
5. アウトラインの「全体目標文字数」「計画ゲート下限」「gate_threshold」の構造化された既知行だけ更新候補にする。重複・自由記述などで安全に特定できなければconflictにし、本文・シーン行・章配分は自動拡張しない。
6. state/outlineの変更前ハッシュ、差分、バックアップ位置をmigration planに記録する。applyはplan hashを照合し、レビュー後の変更があれば停止する。
7. 書込み後に計画メタデータとhealthを読み直し、runtimeをstaleとする。再実行はno-op。本文と既存承認の本文ハッシュは変えない。

旧 `migrate_project_state.py --project P` の目標を変えない移行は維持する。ただしファイルの存在をcompletedとする旧誤動作は修正する。ロールバックはmigration IDを指定し、移行後にユーザーが編集したファイルを上書きしない。

## 8. 出典付き長期記憶

### 8.1 外部エージェントとの分担

Pythonは本文の意味を抽出しない。外部エージェントが対象本文・出典範囲を読み、JSON提案を作る。Pythonは形式・ID・参照・出典ハッシュ・可視範囲を検証する。採用は明示的な操作で、検証成功だけでacceptedにしない。

`build_scene_index.py` の先頭抜粋は `summary_kind=excerpt` と明示し、互換索引として残す。acceptedなscene_outcomeがある場合だけ「意味的要約」として利用する。抜粋で人物知識や伏線の回収を推測しない。

### 8.2 保存形式と最小スキーマ

- `story_memory/proposals/<batch_id>.json`: 未採用提案。既存IDへの異内容上書きは拒否。
- `story_memory/accepted.json`: version、revision、recordsを持つ採用済み台帳。
- `runtime/story_memory_status.json` / `memory_review.md`: 検証・stale・不足・矛盾候補の派生レポート。

共通項目: `id`, `kind`, `text`, `entity_ids`, `available_after_scene`, `sources`, `supersedes`。sourceは `path`, `content_hash`, `line_start`, `line_end` を持つ。すべてproject内の実在する承認済みscene txtへ正規化し、`../`やsymlinkによるproject外参照を拒否する。sourceのscene IDは入力値を信頼せず、canonicalな本文パスから解決する。fact・knowledge・thread・outcomeだけでなくchapter/part summaryも、有効な承認のある本文だけを根拠にできる。企画アウトライン・設定Markdownを作中で実現した事実の根拠として採用しない。

kindは次の6種類に限定する。

- `fact`: 作中で成立した事実。`subject_id`, `predicate`。
- `character_knowledge`: 人物が知った事実。`character_id`, `fact_id`。事実の存在と人物の知識を分離する。
- `thread_event`: 伏線・謎・約束の状態変化。`thread_id`, `event`（opened / progressed / resolved / abandoned）。既存のeventを消さず履歴を積む。
- `scene_outcome`: シーンで実際に変化したこと。`scene_id`。計画上のpurposeとは別。
- `chapter_summary`: 既筆章の要約。`chapter`, `covered_scenes`。
- `part_summary`: 既筆の部の要約。`part_id`, `covered_scenes`。

summaryの `covered_scenes` は明示列挙し、対象の出典ハッシュをすべて持つ。chapter/part全体を覆っていなければpartialと表示する。序盤の本文を書き換えれば、その本文を参照する事実・人物知識・上位要約もstaleになる。factを参照するknowledgeにも失効が伝播する。sourceの承認が失効している間も使用不可とし、理由を示す。`available_after_scene` が自身または参照先の根拠sceneの最大値より前なら提案を拒否する。

採用済み記録は本文が変わっても削除しない。staleを派生判定し、promptから外して再提案を要求する。意味を変えずに出典ハッシュだけ付け替えて「再検証済み」にしない。訂正は新しいIDと `supersedes` で追跡し、置換関係の循環を拒否する。

### 8.3 未来・人物知識の隔離

基準は既存シーンIDの数値順、すなわち読者が読む順序。物語内時刻とは区別し、回想の年表順を自動推測しない。

対象Tへのdraftでは、accepted・非staleで、すべての出典シーンと `available_after_scene` がTより前の記録だけを使う。判定は自身のsourcesだけでなく、参照fact、covered_scenes、supersedesの参照先まで時点条件をたどる。supersessionは対象T時点で有効な置換だけを適用し、未来の訂正が過去時点では有効な旧記録を消さない。現在時点のglobal statusはhealth等の表示用であり、選択候補をglobal activeだけに絞らない。全acceptedから対象Tのstatusを計算する。出典ハッシュの鮮度依存はfact参照等に伝播するが、訂正対象であるsupersedes先がstaleであることだけで新しい訂正もstaleにすることはない。対象T自身の既存本文を改稿する場合も、過去事実として混ぜず別の改稿入力にする。

`author_context` はその時点までに成立した事実・展開、`pov_context` は対象人物の `character_knowledge` が明示している事実だけ。人物が知っていない情報をknowledgeに自動追加しない。視点人物未指定時は「知識未確定」を表示し、全人物の知識を一括投入しない。

未来の本文・結末・先の章の要約は、検索スコアが高くても候補から除外する。対象Scene Ledgerの「今回起こすこと」や企画上の伏線予定は `planning` として区切り、既に起きた事実とラベルを混ぜない。これらの分離は構造上の防御であり、実際のLLMの書き分けは別評価する。

## 9. runtimeへの組込みと文脈量

新しい選択結果を `story_memory_pack.md` として生成し、`related_context_pack.md` とともにdraft promptへ実際に挿入する。対象scene、視点人物、明示された人物・thread IDによる関連付けを優先し、旧作では過去シーンの抜粋検索にフォールバックする。

順序: ①対象の制約と明示参照、②視点人物の知識、③未解決thread、④直前の結果、⑤過去章・部の要約、⑥補助抜粋。必須制約を黙って捨てない。

初期値は最終prompt上限16,000文字、長期記憶枠6,000文字、直前本文枠4,000文字とする。日本語の実トークン数とは別の決定的な予算で、既存 `len(text)//2` は概算としてだけ表示する。任意の記録は記録単位で外し、除外IDと出典pointerを `context_selection.json` に残す。直前本文が枠を超える場合は抜粋であることを明示する。必須情報だけで上限超過なら通常prompt生成を止め、文字数と内訳を表示する。全体目標20万字だから枠を自動倍増することはしない。

## 10. モジュール境界

`prompt_utils.py` は互換入口として残し、今回触る責務だけ段階的に抽出する。

- `novel_agent/errors.py`, `storage.py`: 共通例外、原子的I/O、ロック。
- `length_profiles.py`: 目標値・長さプロファイル・ゲート既定値。
- `runtime_paths.py`: シーンruntime選択とidentity検証。
- `scene_status.py`: 状態導出と共通投影。
- `dependencies.py`: 入力ダイジェストと鮮度検証。
- `project_migration.py`: dry-run・競合検出・apply・rollback。
- `chapter_scaffold.py`: 可変章数の雛形。
- `story_memory.py`: 提案検証・採用・失効・参照整合。
- `memory_context.py`: 時点・人物・予算を考慮した選択と描画。

低層モジュールは `prompt_utils` をimportしない。既存CLIと `novel_agent` は必要箇所から新モジュールを利用する。Markdown解析の全面置換、新しい汎用フレームワーク、既存全文compilerの削除は行わない。

## 11. 共通エージェント入口

ルート `AGENTS.md` を短い入口として追加し、`agent/HUB.md`、`AGENT_GUIDE.md`、各skillへ誘導する。READMEのAntigravity専用表現を「Codex等の外部エージェント」に整理し、既存利用者の例は残す。

執筆手順は「prepare → prompt → 本文をtxtへ保存 → check → 必要な局所改稿 → 再check → 明示approve → 記憶提案 → 検証・採用 → 次scene」とする。approveと記憶acceptは別操作。章末・部末には意味的要約の提案を促すが、自動的に生成済み・採用済みとしない。AGENT_GUIDEの存在しない `compose_agent_package.py` や固定1000〜1500字説明も、現行コマンドとLength Bandへ合わせる。

## 12. 検証と出荷基準

### 自動検証

- 既存87テストを基準に、4不変条件の回帰テストを追加。仕様変更で不正な期待値を直す場合は変更理由と新しい強いassertionを記録し、削除・skip・閾値緩和で緑にしない。
- 20章×5scene×本文2,000字=20万字の合成fixtureを生成する。30k/50k/100kは既存fixtureも継続する。
- 初期化、移行、各種status、後半sceneのprepare/prompt/check/approve/export、再開、章・部のsummary、古い本文の改稿、未来の高類似シーン、破損JSON、ID衝突を一連で検証する。
- 大きさを増やしても最終prompt予算内。全文が紛れ込まない。所要時間・読取ファイル数・prompt文字数を記録するが、環境依存の秒数を品質合格の代用にしない。
- 旧評価suiteは実LLM評価と区別して再実行する。CIのPython 3.8/3.12 matrixで互換性を確認する。テスト依存はpytest==8.3.5に固定して実インストールを含め検証し、3.8を実行する前に対応確認済みとは報告しない。

### 実際のエージェント評価（別工程）

同じ20万字fixtureに、離れたシーン間の事実、人物Aだけが知る秘密、未回収thread、未来にしか出ない固有情報を埋め込む。Codex等の実エージェントへ序盤・中盤・終盤の執筆/改稿/再開を依頼し、モデル・日時・入力prompt・実際に読んだ出典・出力・検査結果・人間の採点を保存する。

評価項目は、過去事実の保持、人物知識の境界、未来情報の漏出、伏線状態、目標Length Band、runtime-first手順、stale後の復旧。未来秘密の漏出と未検査承認は重大失敗とする。長編の読解や文体の評価は人間が根拠箇所付きで判定する。未実施は `not_run` と記録し、ルールベーステスト成功で補完しない。

## 13. 実施順序とレビューの区切り

A. 安全な保存と4不変条件 → B. 20万字プロファイル・移行・可変章数 → C. 出典付き記憶 → D. 文脈統合・共通手順 → E. 長編自動回帰と実エージェント評価。

実装開始時は基準SHAと現在のremote/branchを確認し、進んでいる場合は差分を再調整する。分離した実装ブランチで作業し、対象作品が明示されるまでは移行をscratch fixtureだけで検証する。ユーザーの小説データは変更せず、push・mergeは別途の許可なしに行わない。

各段階は単独でテストできる変更に分ける。A/Bだけでも従来の手動Markdown運用が改善され、Cが未採用の作品でも従来フローを壊さない。コード反映・作品移行はこの設計と実装計画のレビュー後に着手する。
